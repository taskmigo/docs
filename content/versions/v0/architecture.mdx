A Taskmigo system manages one site graph in a user-managed PostgreSQL database.

## Database boundary

Taskmigo owns one configurable PostgreSQL schema, named `taskmigo` by default. It must not access or modify `public` or other user schemas.

Version 0 has no tenant registry, database routing, or `tenant_id`.

## Resource graph

The graph starts at the system's only Site manifest. Every regular runtime resource must be reachable through an `imports` edge.

```text
Site
├── Application: crm
│   ├── Page: dashboard
│   └── Entity: customer
└── Shared resources
    ├── Theme
    └── Policy
```

The one-Site invariant is system-wide. Schema prefixes do not create separate composition roots, so `v0/site` and a future `v1/site` cannot coexist. See [Site cardinality](/versions/v0/resources#site-cardinality).

Version selection happens per edge, so separate branches may resolve the same `(kind, name)` to different revisions. See [Resource model](/versions/v0/resources#imports) for import syntax and resolution.

Translation catalogs are selected by locale rather than imported by consumers. See [v0/translation](/versions/v0/manifests/v0-translation).

## Composition root

The [Site manifest](/versions/v0/manifests/v0-site) imports applications and selects which ones to expose. Each [Application manifest](/versions/v0/manifests/v0-application) declares its own dependencies; resources are never discovered by name.

## Runtime boundary

A valid graph compiles into an immutable Site snapshot. Each request reads one snapshot. Invalid changes retain diagnostics while the current snapshot continues serving traffic.
