# Architecture

A Taskmigo deployment manages one independent site graph in a user-managed PostgreSQL database.

## Database boundary

Taskmigo owns one configurable PostgreSQL schema (default: `taskmigo`). It may create, read, update, and delete objects only in that schema. It must not access or modify `public` or other user schemas.

Taskmigo is not a multi-tenant control plane. The current model has no tenant registry, database routing, or `tenant_id`.

## Resource graph

Every YAML manifest is a resource with a unique identity:

```text
(kind, name)
```

A resource can explicitly depend on other resources through `includes`. The runtime graph begins at one `v0/site` resource. Only resources reachable from that Site are included in runtime.

```text
Site
├── Application: crm
│   ├── Page: dashboard
│   └── Entity: customer
└── Shared resources
    ├── Theme
    └── Policy
```

## Site and application

- **Site** is the composition root for a website or product. The `v0/site` manifest exposes included applications and provides shared brand configuration. See [v0/site](/docs/manifests/v0-site).
- **Application** is a functional module such as CRM, Helpdesk, or Admin. Its public manifest contract is not defined yet.
- An application does not auto-discover resources by name; every dependency must be reachable through the declared graph.

## Runtime boundary

Taskmigo compiles the valid reachable graph into one immutable Site snapshot. Each request reads one snapshot, so it never combines old and new revisions. When a change is invalid, the current snapshot continues serving traffic.
