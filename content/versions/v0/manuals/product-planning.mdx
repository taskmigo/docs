Product planning tracks **delivery state**, not documentation maturity. A capability can have a defined contract and still be only planned for implementation. Use [Product status](/versions/v0/manuals/status) when you need to distinguish defined contracts, RFCs, and unresolved product semantics.

## Delivery states

| Status              | Meaning                                                                                      |
| ------------------- | -------------------------------------------------------------------------------------------- |
| 💡 **Proposal**     | An idea, RFC, or named capability that is not yet ready for implementation.                  |
| 📋 **Planned**      | The capability is accepted and has enough contract or design detail to begin implementation. |
| 🚧 **In Progress**  | Implementation is actively underway.                                                         |
| 🧪 **Verification** | Implementation is complete enough for review, testing, and acceptance checks.                |
| ✅ **Done**         | The capability has passed verification and is accepted as delivered.                         |

## Planning notes

Open decisions do not become a separate delivery state. Keep the capability in its current column and use [Product status](/versions/v0/manuals/status#known-limitations-and-open-decisions) to see unresolved semantics that may block implementation or acceptance.

When a capability moves between columns, update this board from delivery evidence rather than documentation state alone.
