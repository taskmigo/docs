title: Product status
description: Scope boundaries for the initial Taskmigo product contract.
---

The documentation defines the target product contract. It does not imply that every documented capability is already implemented.

## Initial product scope

The first coherent implementation should deliver these capabilities together:

| Area                | Scope                                                                             |
| ------------------- | --------------------------------------------------------------------------------- |
| Identity            | Users, account status, system administrator flag.                                 |
| Teams               | Flat groups and group membership.                                                 |
| Projects            | Active/archive lifecycle, project key, project membership.                        |
| Authorization       | Custom roles, fixed permission catalog, direct and group-derived role assignment. |
| Issue configuration | Issue types, statuses, priorities, workflows.                                     |
| Issues              | Create, read, update, assign, transition, hierarchy, journal, comments.           |
| Auditability        | Immutable authorship plus chronological issue change history.                     |

## Explicitly deferred

The following capabilities are important to the broader mission but are not part of the initial contract: custom fields, time tracking, wiki, repository integration, Gantt planning, issue relations beyond parent/child, saved queries, email ingestion, notifications, attachments, public projects, anonymous access, multi-project issue ownership, plugin compatibility, Redmine API compatibility, and Redmine database compatibility.

Deferral is intentional. These features should be added only after their domain model and permission implications are designed end to end.

## Open product decisions

Authentication provider configuration, issue deletion semantics, configuration-value archival, notification delivery, and import/migration behavior remain separate design decisions. Implementations must not invent externally visible behavior for them merely to complete the core domain.
