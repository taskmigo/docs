---
title: Issues
description: The core unit of work in Taskmigo.
---

An issue is a unit of work owned by exactly one project. Issues use a project-local sequence so people can communicate with compact references such as `TM-42` while the internal ID remains stable.

## Core fields

| Field       | Contract                                                   |
| ----------- | ---------------------------------------------------------- |
| ID          | Stable internal identifier.                                |
| Sequence    | Monotonic integer unique within the project. Never reused. |
| Project     | Owning project. Immutable after creation.                  |
| Type        | Issue type configured for the project.                     |
| Status      | Current workflow status.                                   |
| Priority    | Current urgency classification.                            |
| Subject     | Required short summary.                                    |
| Description | Optional long-form description.                            |
| Author      | User who created the issue. Immutable.                     |
| Assignee    | Optional user or group that is a current project member.   |
| Parent      | Optional issue in the same project.                        |
| Start date  | Optional planned start date.                               |
| Due date    | Optional planned completion date.                          |
| Estimate    | Optional estimated effort in minutes.                      |
| Progress    | Optional integer from 0 through 100.                       |
| Created at  | Creation timestamp.                                        |
| Updated at  | Last mutation timestamp.                                   |

Issue type, status, and priority are referenced by stable identifiers rather than copied labels. Renaming a configuration value therefore updates how existing issues are presented without rewriting issue history.

## Types, statuses, and priorities

Issue types classify the nature of work. A project may enable several types, such as Bug, Task, and Feature.

Statuses describe lifecycle state and are consumed by workflows. A status is not itself permission-aware; permissions belong to roles and transition rules belong to workflows.

Priorities describe urgency independently from status. Changing priority never changes workflow state.

## Assignment

An assignee may be a user or group, but the principal must currently participate in the same project. Assignment does not grant project access. If a group is assigned, Taskmigo does not automatically choose an individual member.

## Hierarchy

An issue may have one parent issue in the same project. Cycles are invalid. Cross-project parents are invalid.

The initial hierarchy is intentionally structural only. Roll-up estimates, automatic progress aggregation, dependency scheduling, and Gantt semantics are separate capabilities rather than implicit side effects of parent/child relationships.

## Mutations and history

Every meaningful issue mutation should produce an auditable journal entry containing the actor, timestamp, and changed values. Comments participate in the same chronological issue activity stream but are distinct records so comment editing policy can evolve independently from field-change history.
