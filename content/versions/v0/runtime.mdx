Taskmigo never activates a manifest directly. It resolves and validates a
candidate Site graph, compiles that graph into an immutable snapshot, then makes
the snapshot current in one atomic switch.

<Callout title="The current Site stays available" type="info">
  Building or rejecting a candidate does not disturb the current snapshot. A replacement becomes
  visible only after the complete candidate graph is valid.
</Callout>

## From change to active snapshot

Create, update, delete, and package import all enter the same lifecycle.

<Steps>
  <Step>

### Find the affected graph

Taskmigo starts with the changed resource and follows reverse `imports`
references to the Site. Resources outside its reachable graph are
not revalidated.

Translation catalogs are tracked by effective locale rather than explicit
reference edges. Changing a translation resource also marks the Site graph when
it uses that locale catalog.

  </Step>
  <Step>

### Resolve a candidate graph

The `v0/site` manifest is resolved from its existing declarations. Site
Site and Application imports select a revision per graph edge; translation
catalogs are attached for the effective locale.

Separate branches may select different versions of the same `(kind, name)`.
Both revisions can coexist in the candidate graph and, if valid, its snapshot.
See [Resource model](/versions/v0/resources#imports) for reference
and version selection rules.

  </Step>
  <Step>

### Validate the complete candidate

Activation requires all of the following to succeed:

- YAML parsing and common manifest metadata
- kind-specific schema validation
- import hierarchy, dependency resolution, and graph checks
- security constraints

Taskmigo validates the complete reachable graph before changing runtime state.

  </Step>
  <Step>

### Build an immutable snapshot

A valid candidate is compiled into one Site snapshot containing every selected
resource revision and the normalized runtime model. Later resource revisions
cannot alter this snapshot.

  </Step>
  <Step>

### Switch the current snapshot

Taskmigo stores the replacement and atomically makes it current in PostgreSQL.
New requests read the replacement. Requests already in progress may finish on
the snapshot they started with.

  </Step>
</Steps>

## Validation outcome

<Tabs items={['Valid candidate', 'Invalid candidate']}>
  <Tab>

The candidate proceeds through snapshot build and activation. There is no
separate publish step or manual activation state.

  </Tab>
  <Tab>

Validation stops before snapshot build. Taskmigo stores structured diagnostics
with the affected revisions and leaves runtime state unchanged.

<Callout title="Diagnostics are safe to display" type="info">
  A diagnostic identifies the error, manifest path, and source location when available. It must not
  expose credentials, connection strings, or data from schemas that Taskmigo does not own.
</Callout>

  </Tab>
</Tabs>

## Dependency recovery RFC

<Callout title="RFC: proposed behavior, not the current contract" type="warn">
  The resource graph now supports `Site → Application → Page`, but dependency recovery order after a
  Page becomes invalid or valid again is not yet a defined runtime contract. This section records
  the intended behavior. Details may change before the proposal becomes defined.
</Callout>

The proposal revalidates resources in dependency order. For the current graph, consider an Application that imports a Page:

<Tabs items={['Dependency breaks', 'Dependency recovers']}>
  <Tab>

1. The Page becomes missing or invalid.
2. Candidate validation fails for the Application, then the Site.
3. The candidate follows the invalid outcome above.

  </Tab>
  <Tab>

1. The Page becomes valid again.
2. Taskmigo validates the Page, then the Application, then the Site.
3. The valid graph continues to snapshot build and activation.

  </Tab>
</Tabs>

The proposed recovery process re-resolves existing declarations; it does not
rewrite dependent manifests. Deleting a resource follows the same path as an
invalid dependency: the candidate fails while the last valid snapshot remains
active.

## Package boundary

<Callout title="A package is activated as one unit" type="success">
  Import validates the complete package, including the one-Site invariant and reference hierarchy,
  before resolving dependencies inside the target Taskmigo schema. A failed import must not leave a
  partially active runtime state.
</Callout>

Export produces a portable package of canonical YAML. Importing that package
still runs the lifecycle above; exported resolution results are not trusted as
runtime state.
