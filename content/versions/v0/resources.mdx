These rules apply to every manifest. Kind reference pages document only their additional fields and validation.

## Common shape

```yaml
kind: v0/site
name: root
version: 1.0.0 # optional

imports:
  - v0/application/home@^1.2.0

spec:
  # kind-specific configuration
```

| Field     | Rule                                                                                                                 |
| --------- | -------------------------------------------------------------------------------------------------------------------- |
| `kind`    | Required schema identifier in its complete versioned form, such as `v0/application`.                                 |
| `name`    | Required resource name matching `[a-zA-Z0-9_-]+`.                                                                    |
| `version` | Optional immutable [Semantic Version](https://semver.org/) tag for this revision.                                    |
| `imports` | Optional dependency references when the selected kind allows them. Each `(kind, name)` may appear once per manifest. |
| `spec`    | Required kind-specific configuration.                                                                                |

## Identity and revisions

The pair `(kind, name)` identifies a resource. The optional `version` tags one of its revisions; it does not change the identity or select the manifest schema.

Every semantic change creates a revision that is validated independently. A tagged revision is immutable, and one version tag cannot refer to different content. An untagged revision may be selected only by a reference without a version constraint.

### Site cardinality

A valid Taskmigo system contains exactly one logical Site resource. The Site may have multiple revisions under the revision rules above; those revisions do not create additional Sites.

Cardinality is enforced across the Site kind family rather than per `(kind, name)`. A different name or schema prefix cannot establish a second Site:

```yaml
# Invalid in the same system
kind: v0/site
name: primary
---
kind: v1/site
name: replacement
```

Creating or importing a second Site fails validation. A manifest set containing both `v0/site` and `v1/site` resources is invalid.

## Imports

The field uses `<kind>/<name>` to select the latest revision or append `@<version>` to apply a SemVer constraint:

```yaml
imports:
  - v0/application/home@^1.2.0
```

Taskmigo accepts exact versions, caret ranges such as `^1.2.0`, and tilde ranges such as `~1.2.0`.

`imports` declare dependency edges. A Site may import Applications, and only an Application may import Pages.

### Uniqueness scope

Within one field of one manifest, references are unique by `(kind, name)`. A different or omitted version constraint does not make a second reference valid:

```yaml
# Invalid: both entries import v0/application/home
imports:
  - v0/application/home@^1.0.0
  - v0/application/home@^2.0.0
```

The rule is not graph-wide. Different manifests may resolve the same identity to different versions, and both revisions may coexist in one snapshot.

### Reference ability

Use the matrix from left to right: choose the manifest that declares `imports`, then find the kind it references.

**Legend:** ✅ allowed · ❌ not allowed · — same kind

| Importer         | `v0/site` | `v0/application` | `v0/page` | `v0/translation` |
| ---------------- | :-------: | :--------------: | :-------: | :--------------: |
| `v0/site`        |     —     |        ✅        |    ❌     |        ❌        |
| `v0/application` |    ❌     |        —         |    ✅     |        ❌        |
| `v0/page`        |    ❌     |        ❌        |     —     |        ❌        |
| `v0/translation` |    ❌     |        ❌        |    ❌     |        —         |

This matrix is exhaustive: every relationship marked ❌ is invalid.

<Callout title="Translation catalogs are never reference targets" type="warn">
  No manifest may import `v0/translation`. A translation manifest may declare the common `imports`
  field only as an empty list. Taskmigo attaches the effective locale catalog automatically when it
  builds a Site snapshot.
</Callout>

### Resolution

<Steps>
  <Step>

### Find the resource

Parse the reference and match its exact `(kind, name)`.

  </Step>
  <Step>

### Select a revision

Select the latest revision when no constraint is present; otherwise select the highest tagged version that satisfies the constraint.

  </Step>
  <Step>

### Validate the selection

The selected revision must be valid. Resolution never falls back to an older or lower version.

  </Step>
  <Step>

### Record the snapshot

Record the selected revision so later changes cannot alter the active snapshot.

  </Step>
</Steps>

Malformed references, disallowed kind pairs, missing resources, duplicate references, unsatisfied constraints, invalid selected revisions, and Site cardinality violations fail resolution.

<Callout title="Latest is resolved at build time" type="info">
  An unconstrained reference follows the latest revision when a new snapshot is built. Existing
  snapshots remain unchanged.
</Callout>
