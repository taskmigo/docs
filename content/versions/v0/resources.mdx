# Resource model

A resource is an independent YAML manifest. YAML is the source of truth; normalized data, diagnostics, and runtime snapshots are derived from it.

Every manifest kind uses the rules on this page. A kind reference only documents the fields and validation specific to that kind.

## Common manifest shape

```yaml
kind: v0/page
name: users
version: 1.0.0 # optional

includes:
  - kind: v0/entity
    name: user
    version: ^1.2.0 # optional

spec:
  # kind-specific configuration
```

| Field | Rule |
| --- | --- |
| `kind` | Required resource type, including its API version. Version 0 kinds use the complete `v0/...` form. |
| `name` | Required resource name. Together, `kind` and `name` identify a resource. |
| `version` | Optional immutable [Semantic Version](https://semver.org/) tag for this revision. |
| `includes` | Optional explicit list of resources on which this resource depends. |
| `spec` | Required configuration defined by the selected `kind`. |

## Resource identity

Taskmigo identifies a resource by the pair `(kind, name)`, not by `name` alone. Names must therefore be unique within one kind, while two different kinds may use the same name.

Kind names are always versioned. Use `v0/application`, `v0/page`, and similar complete values in both top-level `kind` fields and `includes[].kind`. Values such as `application`, `page`, or `Page` do not identify a versioned manifest contract and are invalid.

The API version in `kind` is separate from the optional resource `version`:

- `kind: v0/application` selects the version 0 application schema.
- `version: 1.2.0` tags one immutable revision of a particular application resource.

## Revisions and version tags

A revision is one saved state of a resource. Every semantic change creates a new revision, and each revision is validated independently.

A revision with a `version` tag is immutable. To change its content, create another revision with a new SemVer tag or leave the new revision untagged. The same version tag cannot refer to different content.

An untagged revision may be the latest revision and may be selected by an include without a version constraint. It cannot satisfy `includes.version`, because a constraint can only be evaluated against tagged SemVer versions.

## Includes

An include identifies a dependency by the exact pair `(kind, name)`:

```yaml
includes:
  - kind: v0/application
    name: home
    version: ^1.2.0
```

The optional `version` is a SemVer constraint. Version 0 supports exact versions, caret ranges such as `^1.2.0`, and tilde ranges such as `~1.2.0`.

Resolution works as follows:

1. Taskmigo finds the resource with the exact included `kind` and `name`.
2. Without `includes.version`, it selects that resource's latest revision.
3. With `includes.version`, it selects the highest tagged version satisfying the constraint.
4. The selected revision must be valid. Taskmigo does not silently fall back to an older revision or lower version.
5. The selected revision is recorded in the Site snapshot, so later resource revisions do not alter an already active snapshot.

Missing resources, duplicate includes, unsatisfied constraints, dependency cycles, and invalid selected revisions make resolution fail. Resolution is deterministic and remains within the same Taskmigo schema.

## Good to know

A version constraint controls which revision may be selected; it does not select the manifest schema. The `kind` value selects the schema, while `includes.version` selects a compatible revision of that kind.

Omitting `includes.version` follows the latest revision when a new snapshot is built. It does not mutate snapshots that are already active.
