## Purpose

A Policy is a global manifest, like Translation: Taskmigo selects it for every Site snapshot rather than importing it from another manifest. It has only two effects: `allow` and `deny`. The target gives that decision its meaning.

| Target      | `allow`                                 | `deny`                                          |
| ----------- | --------------------------------------- | ----------------------------------------------- |
| Request     | Let the matching Page or API route run. | Reject the request before its handler runs.     |
| Data record | Permit a matching record to be read.    | Exclude matching records in the database query. |
| Data field  | Permit a selected field to be returned. | Remove the field from the result.               |
| UI          | Render a policy-managed target.         | Do not render the target.                       |

UI policy is not a security boundary. A hidden UI target must still be protected by request and data rules.

## Example

```yaml
kind: v0/policy
name: customer-access

spec:
  rules:
    - id: allow-finance-invoices
      effect: allow
      target:
        request:
          method: GET
          path: /invoices/**
      when: 'principal.groups.contains("finance")'

    - id: allow-public-or-owned-projects
      effect: allow
      target:
        data:
          resource: project
          operation: read
      when: >-
        resource.visibility == "public" ||
        resource.ownerUsername == principal.username

    - id: deny-email-to-non-admins
      effect: deny
      target:
        data:
          resource: customer
          fields: [email]
      when: '!principal.roles.contains("admin")'

    - id: deny-admin-application
      effect: deny
      target:
        ui:
          application: admin
      when: '!principal.roles.contains("admin")'
```

A request target specifies its route with `method` and `path`. A data target identifies a `resource`, an `operation`, and optionally `fields`; a denied field is removed from the response. A UI target identifies an `application`, `page`, or `componentId` (the value of `data-component-id`).

## Conditions and database filtering

`when` is a compact predicate language—not a general-purpose Expression and never raw SQL. It supports `&&`, `||`, `!`, parentheses, comparisons, `in` / `not in`, literals, lists, and a fixed set of SQL-compilable functions such as `contains()` and `startsWith()`.

It may read `principal.username`, `principal.roles`, `principal.groups`, and phase-specific request, resource, or UI context. It cannot call arbitrary functions, run templates, perform I/O, or cause side effects. This lets the runtime give one rule equivalent application and database evaluation.

When a policy governs which records a caller may read, the runtime compiles its predicate to a parameterized SQL `WHERE` clause and applies it as part of the database query. It must not fetch candidate records and then filter them in application memory. A predicate that cannot be compiled for a data source makes the affected snapshot invalid; it never falls back to an unfiltered query.

The data-resource contract defines the logical field-to-database mapping separately. A database column or computed field with a SQL translation may appear in a data predicate. A field computed only in the application layer may not decide record or field access; using it there makes the snapshot invalid. It may be used only in non-data phases where it cannot grant access to protected data.

## Evaluation

The policy target decides which route types it applies to; Page and API routes use the same request matching contract.

- `deny` takes precedence over `allow`.
- Request and data-record access require a matching `allow`; otherwise access is denied.
- A matching data-field `deny` removes the field. The runtime omits it from `SELECT` where possible and always removes it before JSON serialization.
- UI remains visible unless a matching UI `deny` applies. A UI `allow` can make an explicitly policy-managed target render, but it never overrides a matching `deny`.
- Rules are evaluated from the snapshot-pinned policy revisions, so an active request does not change behavior mid-execution.

## Global selection

Policies do not participate in `imports` and no manifest may import `v0/policy`. A policy change rebuilds affected Site snapshots. Each snapshot pins the policy revision it selected.
