## Purpose

A Policy is a global manifest, like Translation: Taskmigo selects it for every Site snapshot rather than importing it from another manifest. A policy controls three points:

| Point | Effects | Purpose |
| --- | --- | --- |
| Incoming request | `allow`, `deny` | Decide whether a matching route may run. |
| Outgoing response | `deny`, `redact` | Block a response or remove fields from a JSON response. |
| UI | `show`, `hide` | Control whether an application, page, or identified UI instance renders. |

UI policy is not a security boundary. A hidden UI target must still be protected by an incoming-request rule.

## Example

```yaml
kind: v0/policy
name: customer-access

spec:
  rules:
    - id: allow-customer-read
      effect: allow
      target:
        request:
          method: GET
          path: /customers/**
      when:
        field: principal.roles
        operator: contains
        value: customer-reader

    - id: redact-customer-email
      effect: redact
      target:
        response:
          request:
            method: GET
            path: /customers/**
          contentType: application/json
          fields:
            - customers.*.email
      when:
        not:
          field: principal.roles
          operator: contains
          value: customer-admin

    - id: hide-admin
      effect: hide
      target:
        ui:
          application: admin
      when:
        field: principal.roles
        operator: contains
        value: admin
```

A request target specifies its route with `method` and `path`. A response target adds `contentType: application/json` and `fields`; each matching field is removed. A UI target identifies an `application`, `page`, or `componentId` (the value of `data-component-id`).

## Conditions and database filtering

Policy conditions are a declarative, portable DSL—not general-purpose Expressions and never raw SQL. This lets one rule have equivalent runtime and database evaluation.

A condition is one of:

- A comparison: `field`, `operator`, and `value`.
- `all` or `any`: an array of nested conditions.
- `not`: one nested condition.

The initial operators are `eq`, `ne`, `in`, and `contains`. Conditions may read the authenticated `principal.username`, `principal.roles`, and `principal.groups`. A future data-resource contract may additionally expose logical record fields; it must map each supported field to its database representation.

When a policy governs which records a caller may read, the runtime compiles its condition to a parameterized SQL `WHERE` predicate and applies it as part of the database query. It must not fetch candidate records and then filter them in application memory. A condition that cannot be compiled for a data source makes the affected snapshot invalid; it never falls back to an unfiltered query.

The data-resource contract will define its field-to-database mapping separately. Policy owns the condition syntax and its security semantics, while a data source owns the physical schema.

## Evaluation

The policy target decides which route types it applies to; Page and API routes use the same request matching contract.

- `deny` takes precedence over `allow`; no matching request rule denies the request.
- All matching `redact` rules remove their selected JSON fields. Without a response rule, an allowed response is unchanged.
- `hide` takes precedence over `show`. UI is hidden by default only when its target is managed by UI policy.
- Rules are evaluated from the snapshot-pinned policy revisions, so an active request does not change behavior mid-execution.

## Global selection

Policies do not participate in `imports` and no manifest may import `v0/policy`. A policy change rebuilds affected Site snapshots. Each snapshot pins the policy revision it selected.
