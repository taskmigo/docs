---
title: Authorization
description: Resolve project access and permissions without ambiguous precedence.
---

Authorization is additive. The implementation must not encode hidden precedence between direct and group-derived access.

## Resolution algorithm

For user `U` and project `P`:

1. Reject project-scoped access when the user account is not active, except installation-level recovery operations explicitly reserved for a system administrator.
2. Load direct project membership for `U`.
3. Load groups containing `U`, then project memberships for those groups.
4. Union all roles assigned through those memberships.
5. Union all permissions granted by the effective roles.
6. Evaluate the required permission.
7. Apply operation-specific domain rules after the permission check.

Use set semantics at every union. A duplicated role or permission must not change the result.

## Workflow authorization

A status transition requires both `issue:transition` and a workflow transition whose `allowed_roles` intersects the actor's effective roles.

The workflow check consumes **effective roles**, not effective permissions, because transition policy is deliberately expressed in terms administrators can see and configure as project roles.

## Caching

Effective authorization is derived from users, group membership, project membership, role assignments, and role permissions. Any cache must either be invalidated by changes to all of those inputs or have a bounded lifetime acceptable for security decisions.

A correct uncached query is preferred to a stale permission cache. Do not cache an authorization decision without a defined invalidation strategy.

## Query boundary

Read endpoints may use a database query that incorporates authorization filtering rather than loading every project and filtering in memory. The semantics must remain identical to the resolution algorithm above.
