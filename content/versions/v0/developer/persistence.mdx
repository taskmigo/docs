---
title: Persistence
description: Database constraints and transaction boundaries for the Taskmigo core.
---

Use a relational database for the core model. Membership, authorization, workflow configuration, issue hierarchy, and audit history all benefit from foreign keys, uniqueness constraints, and transactional writes.

## Required constraints

| Data | Constraint |
| --- | --- |
| User username | Unique. |
| User normalized email | Unique. |
| Group membership | Unique `(group_id, user_id)`. |
| Project key | Unique. |
| Project membership | Unique `(project_id, principal_type, principal_id)`. |
| Member role | Unique `(project_member_id, role_id)`. |
| Role permission | Unique `(role_id, permission_key)`. |
| Issue sequence | Unique `(project_id, sequence)`. |
| Workflow selection | Unique `(project_id, issue_type_id)`. |
| Workflow transition | Unique `(workflow_id, from_status_id, to_status_id)`. |

Polymorphic principal references (`USER` or `GROUP`) require application and database-level care because a conventional foreign key cannot target two tables. Prefer an explicit principal model if the selected persistence stack makes polymorphic integrity difficult to enforce safely.

## Issue sequence allocation

Issue sequence allocation must be concurrency-safe. Two simultaneous issue creations in the same project must receive different values without relying on read-then-write logic outside a lock or atomic database primitive.

Gaps are acceptable after a rolled-back or abandoned allocation. Reuse is not.

## Mutation transactions

The following must be atomic:

- issue creation and initial journal entry;
- issue field update and journal entry;
- workflow transition and journal entry;
- membership change and its audit event when administrative auditing is implemented;
- group membership mutation that affects effective project access.

External side effects such as email or webhooks must not be delivered inside the database transaction. Persist an outbox event in the same transaction when reliable asynchronous delivery is later introduced.

## Optimistic concurrency

Issue updates should carry a version or equivalent optimistic concurrency token. An update based on stale state must fail rather than silently overwrite another actor's changes. Transition validation must run against the same version that is persisted.
