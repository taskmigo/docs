# Architecture

A Taskmigo deployment manages one independent site graph in a user-managed PostgreSQL database.

## Database boundary

Taskmigo owns one configurable PostgreSQL schema (default: `taskmigo`). It may create, read, update, and delete objects only in that schema. It must not access or modify `public` or other user schemas.

Taskmigo is not a multi-tenant control plane. The current model has no tenant registry, database routing, or `tenant_id`.

## Resource graph

Every YAML manifest is a resource with a unique identity:

```text
(kind, name)
```

A resource can explicitly depend on other resources through `includes`. The runtime graph begins at one `Site` resource. Only resources reachable from that Site are included in runtime.

```text
Site
├── App: crm
│   ├── Page: dashboard
│   └── Entity: customer
└── Shared resources
    ├── Theme
    └── Policy
```

## Site and App

These concepts describe the planned core composition model; their YAML schemas are not defined yet.

- **Site** is the single composition root for a website or product. It exposes Apps at route prefixes and provides shared runtime defaults.
- **App** is a functional module such as CRM, Helpdesk, or Admin. It owns internal navigation and entry points, but not its public route prefix.
- A Site decides which Apps are exposed and at which paths. An App does not auto-discover resources by name; every dependency must be reachable through the declared graph.

## Runtime boundary

Taskmigo compiles the valid reachable graph into one immutable Site snapshot. Each request reads one snapshot, so it never combines old and new revisions. When a change is invalid, the current snapshot continues serving traffic.
